## 一、系统背景与业务范围

### 1.1 背景

某高校教务管理目前主要依靠 Excel 台账与线下纸质表格完成：每学期排课由教务员手工登记，选课靠学生填表、教师汇总，成绩由教师单独保存 Excel 后交给教务员合并。由此产生四类问题：

1. **重复录入**：同一名学生的信息在学籍表、选课表、成绩表中各存一份，改一处忘一处；
2. **约束失效**：教学班超额、同一学生重复选课、成绩录入超出 0—100，靠人工核对难以完全拦住；
3. **并发冲突**：选课高峰期多人同时抢最后一个名额，手工登记无法保证"已选人数"与"实际选课记录"一致；
4. **统计困难**：课程选课人数、教师工作量、专业学分完成情况需临时拼表，口径不一。

本系统面向上述问题，建立一个以数据库为核心的教学管理小型应用，覆盖"基础数据 — 排课 — 选课 — 成绩 — 统计"主链路。

### 1.2 业务范围（做什么）

| 编号 | 业务域 | 范围 |
|---|---|---|
| S1 | 基础数据管理 | 院系、专业、学生、教师、课程的建档与维护 |
| S2 | 课程与教学班管理 | 课程开设、按学期为课程排教学班（指定教师、上课时间、教室、容量） |
| S3 | 选课管理 | 学生选课、退课；容量与重复选课校验 |
| S4 | 成绩管理 | 教师录入、修改本人教学班的成绩；学生查询本人成绩 |
| S5 | 统计与查询 | 课程选课人数、教师工作量、学生成绩单与学分绩点、课程成绩分布 |

### 1.3 不在范围内（明确不做）

在线考试与题库、学费缴纳、宿舍与后勤、教师评教、与学校现有教务系统的数据对接、移动端与 Web 前端。
**说明**：明确列出"不做什么"是为了把实体范围锁死——数据库设计课最容易被"什么都想要"拖垮。

### 1.4 规模假设（用于后文索引与性能讨论的依据）

| 对象 | 量级 | 依据 |
|---|---|---|
| 在校学生 | 约 20 000 人 | 一所中型高校规模 |
| 教师 | 约 1 500 人 | 师生比约 1:13 |
| 课程（课程库） | 约 3 000 门 | 全校课程库累计 |
| 每学期教学班 | 约 1 200 个 | 每班平均约 60 人 |
| 每学期选课记录 | 约 7 万条 | 人均 3—4 门 |
| 历史选课记录 | 5 年累计约 70 万条 | 用于说明"成绩表随时间膨胀" |

## 二、用户角色与主要操作

### 2.1 角色清单

| 角色 | 关注的数据 | 核心操作 | 明确不做 |
|---|---|---|---|
| **学生** | 课程、教学班、本人的选课与成绩 | 浏览课程与教学班；选课、退课；查询本人成绩单与已修学分 | 不能查看他人成绩；不能自行改成绩 |
| **教师** | 本人教学班、选课学生名单、成绩 | 查看本人教学班与学生名单；录入、修改本人教学班成绩；查看本班选课人数与成绩分布 | 不能给非本人教学班录成绩 |
| **教务管理员** | 院系、专业、学生、教师、课程、教学班 | 维护基础数据；开设课程与教学班；设定容量与选课时间窗口；导出统计报表 | 不直接改学生成绩（成绩由教师负责） |
| **系统管理员** | 账号、权限、备份 | 账号与权限维护、数据备份与恢复 | 本项目仅在数据层预留，不实现界面 |

### 2.2 角色与数据的权限边界【隐含】

需求原文只说"学生、教师、课程、教学班、选课、成绩"，没有说明权限。但以下三条在真实教务系统中必须成立，否则会出现"学生改自己成绩""教师改别人班成绩"这类越权：

- 学生只能读写"本人"的选课与成绩记录；
- 教师只能读写"本人所授教学班"的成绩；
- 成绩一旦被教务处归档，教师不可再改（本项目以"是否锁定"字段或状态位简化处理）。

**处理方式**：数据库层保证"数据归属正确"（成绩挂在选课记录上，选课记录属于具体学生、属于具体教学班，教学班属于具体教师），应用层负责校验"当前登录者是否为该记录的所有者"。

## 三、核心业务流程

### 3.1 排课（每学期开学前，教务管理员）

1. 确认本学期开课清单（从课程库选取课程）；
2. 为每门课程指定任课教师、上课时间、教室、容量，生成**教学班**；
3. 系统校验：同一教师同一时间段不得安排两个教学班；同一教室同一时间段不得冲突；
4. 提交后教学班状态置为"待选课"；
5. 开放选课窗口（设定起止时间）。

**关键点**：课程（Course）与教学班（TeachingClass）是一对多——同一门课不同学期、不同教师、不同时间会开出多个班。这一点是学生最容易漏的实体划分错误。

### 3.2 选课（选课窗口内，学生）

1. 学生查询可选教学班（按课程名、教师、时间筛选）；
2. 选择目标教学班，提交选课；
3. 系统依次校验：是否在选课窗口内 → 教学班是否已满（已选人数 < 容量）→ 是否重复选课 → 是否与已选课程时间冲突 → 是否满足先修要求【已确认：不做先修校验】；
4. 校验通过：写入选课记录（状态"已选"），教学班已选人数 +1；
5. 任一步失败：整体回滚，给出具体原因（"名额已满"/"已选过该班"）。

**关键点**：第 3—4 步必须在**同一个事务**内完成。多人同时抢最后一个名额时，若不加锁或不做条件更新，会出现超选（已选人数 > 容量）。

### 3.3 退课（选课窗口内，学生）

1. 学生查看本人已选教学班；
2. 申请退课；
3. 系统校验：是否在退课窗口内 → 是否已录入成绩（已录成绩不允许退）；
4. 删除（或置为"已退"）选课记录，教学班已选人数 −1。

**关键点**：退课与"已选人数"的维护同样要在事务内完成，否则人数与记录数会长期不一致。

### 3.4 成绩录入（学期末，教师）

1. 教师选择本人教学班；
2. 系统列出该班全部选课学生；
3. 教师逐个录入成绩（0—100，可为空表示未录入）；
4. 提交前校验：成绩范围、是否有遗漏；
5. 提交后成绩写入选课记录，学生端可查询。

**关键点**：成绩是**选课记录（enrollment）的属性**，不是学生的属性，也不是课程属性——一个学生有多门课的成绩，一门课有多个学生的成绩。

### 3.5 统计与查询（随时，按角色）

- 学生：本人成绩单（课程、学分、成绩、绩点）、已修学分合计；
- 教师：本人教学班的选课人数、成绩分布（平均分、最高分、及格率）；
- 教务管理员：按课程/教师/专业/学期统计选课人数、教师工作量（教学班数、学生人数）。

**关键点**：这些统计都是多表连接 + 聚合，涉及学生、选课、教学班、课程、教师 4—5 张表，对应作业"至少一个涉及 3 张及以上数据表的业务操作或查询"的要求。

## 四、核心数据

| 数据对象 | 说明 | 关键属性（概念层，不含类型） |
|---|---|---|
| 院系 | 教学组织的一级单位 | 院系号、院系名 |
| 专业 | 隶属院系，学生归属专业 | 专业号、专业名、所属院系、学制 |
| 学生 | 在校学生 | 学号、姓名、性别、出生日期、入学年份、所属专业、班级 |
| 教师 | 授课教师 | 工号、姓名、性别、职称、所属院系 |
| 课程 | 课程库中的课程（不区分学期） | 课程号、课程名、学分、学时、课程性质（必修/选修）、开课院系 |
| 教学班 | 某学期为某课程开出的具体班级 | 教学班号、课程、任课教师、学期、上课时间、教室、容量、已选人数 |
| 选课记录 | 学生与教学班的对应关系，并承载成绩 | 学生、教学班、选课时间、状态、成绩 |

**关系概览**（详细 E-R 在任务二给出）：

- 院系 1 : N 专业，院系 1 : N 教师，专业 1 : N 学生；
- 课程 1 : N 教学班，教师 1 : N 教学班；
- 学生 M : N 教学班，通过**选课记录**拆分，并携带"成绩、选课时间"两个**联系属性**。

## 五、业务规则与数据约束

> 分类口径：**【库】** 由数据库约束（主键/外键/唯一/CHECK）保证；**【程】** 由程序逻辑（含事务）保证；**【人】** 由管理流程保证。
> 每条规则都标注了落地方式——这是评分表里"业务规则合理性"的主要看点，规则写得再漂亮，落不了地也不算分。

| 编号 | 业务规则 | 落地方式 | 具体实现 |
|---|---|---|---|
| B1 | 学号全校唯一，且不为空 | 【库】 | 以 `student_no` 为业务主键，天然唯一非空 |
| B2 | 工号全校唯一，且不为空 | 【库】 | 以 `teacher_no` 为业务主键 |
| B3 | 每个专业必须属于且仅属于一个院系 | 【库】 | `major.dept_id` 外键 NOT NULL |
| B4 | 每名学生必须属于一个专业 | 【库】 | `student.major_id` 外键 NOT NULL |
| B5 | 课程号唯一；学分取值 0.5—10，且为 0.5 的倍数 | 【库】 | `course.credit` CHECK (credit > 0 AND credit <= 10 AND credit*2 = FLOOR(credit*2)) |
| B6 | 教学班必须指定一名教师和一门课程 | 【库】 | `teaching_class.teacher_id` / `course_id` 外键 NOT NULL |
| B7 | 教学班容量必须为正数 | 【库】 | `teaching_class.capacity` CHECK (capacity > 0) |
| B8 | 已选人数不得超过容量 | 【库+程】 | CHECK (enrolled_count <= capacity)；并发下由选课事务条件更新保证 |
| B9 | 同一学生不能重复选同一教学班 | 【库】 | `UNIQUE(student_id, class_id)` |
| B10 | 成绩取值 0—100，未录入时为空 | 【库】 | CHECK (score IS NULL OR (score >= 0 AND score <= 100)) |
| B11 | 成绩只能挂在"已选课"记录上，退课后成绩随之失效 | 【库】 | 成绩字段置于 enrollment 表，删除选课记录即删除成绩 |
| B12 | 已录入成绩的选课记录不允许退课 | 【程】 | 退课事务中校验 score IS NULL |
| B13 | 同一教师同一学期同一时间段不得安排两个教学班 | 【库+程】 | UNIQUE(teacher_id, semester, time_slot)；程序给出友好提示 |
| B14 | 同一教室同一学期同一时间段不得安排两个教学班 | 【库】 | UNIQUE(classroom, semester, time_slot) |
| B15 | 只有教务管理员能维护基础数据，教师只能录本人教学班成绩 | 【程】 | 应用层按登录角色的权限校验 |
| B16 | 选课、退课只能在教务管理员设定的选课窗口内进行 | 【程】 | 与 `selection_window` 配置比较当前时间 |

## 六、需求分类

### 6.1 明确需求（需求文档/常理已明确）

选课与退课、成绩录入与查询、课程与教学班管理、基础数据维护、按课程与教师的统计。

### 6.2 隐含需求（原文未写但业务上必须成立）

| 隐含需求 | 为什么必须 | 对应规则 |
|---|---|---|
| 并发选课不能超选 | 选课高峰期多人抢最后名额 | B8 |
| 成绩归属必须精确到"某学生某教学班" | 否则无法区分同一学生不同课程的成绩 | B11 |
| 教师只能操作自己的教学班 | 否则越权改分 | B15 |
| 已录成绩不可退课 | 否则成绩凭空消失 | B12 |
| 教学班与课程必须分离 | 同一门课多学期、多教师重复开设 | 四、核心数据 |
| 选课时间窗口 | 选课结束后不应还能选 | B16 |

### 6.3 待确认需求（评审结论）

| 编号 | 问题 | 影响 |
|---|---|---|
| Q1 | 是否允许跨专业选课？是否限制每学期选课门数上限？ | 影响选课校验规则与是否新增规则 |
| Q2 | 是否需要"先修课程"校验？ | 若需要，要新增 course_prerequisite 表（多对多自联系） |
| Q3 | 补考/重修成绩如何记录：覆盖原成绩，还是新增一条记录？ | 影响 enrollment 是否要加"考试类型/是否重修"字段 |
| Q4 | 绩点（GPA）是由系统算还是只存成绩？ | 影响是否要存绩点字段、成绩到绩点的映射表 |
| Q5 | 选课窗口是全局统一，还是按年级/专业分批？ | 影响选课窗口表的粒度 |

**结论（2026-11-21 组内确认，据此进入概念设计）**：

- Q1 → 允许跨专业选课，不限制每学期门数；
- Q2 → 不做先修课程校验（否则要增加课程自联系的多对多表，14 天排期内不划算）；
- Q3 → 重修覆盖原成绩，另用 `attempt` 记录修读次数；
- Q4 → 绩点由成绩与学分的映射规则计算，不设冗余字段存储；
- Q5 → 选课窗口全局统一一个，作为配置项而非独立表。

**影响**：以上结论直接决定概念设计的实体个数（7 张表，不含选课窗口表）与"选修"联系的属性（多出 `attempt`）。若评审后修改结论，需同步更新本文档第 4、5 节与任务二的实体属性表。

## 七、AI 辅助过程记录

Prompt 原文、模型输出与逐条人工判断，统一记录在 [`07_AI辅助过程/AI交互记录.md`](../07_AI辅助过程/AI交互记录.md)（按日期追加，每条标注落到本报告的第几节）。本报告正文只保留复核对结论的影响。

成稿前的人工复核要点（也是评审时会被追问的点）：

- **角色是否漏**：模型常见只给学生和教师，漏掉"教务管理员"——而排课、开教学班、设选课窗口全是它的职责；
- **规则是否可判定**：类似"选课过程应公平公正"的表述无法落成约束，一律改写为"已选人数不得超过容量"这类可验证的形式；
- **三类需求是否分开**：明确需求、隐含需求、待确认需求必须分开标注，否则看不出哪些是模型给的、哪些是我推出来的；
- **越权风险**：模型通常不区分"学生只能看自己的成绩"，这类权限边界必须补。
