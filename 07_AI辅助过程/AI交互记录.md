## 一、2026-11-20　T0　分工与进度规划

- **使用工具**：DeepSeek 编码助手
- **目的**：把课程大作业的六个任务切成三人可执行的分工，并排出进度
- **Prompt（原文）**：

```
这个文件夹里面有一个word文档，这是我数据库的大作业，我已经完成了分组，我是组长，
请帮我做完根据文档里的要求先做一个分工，我们的选题是高校教学管理系统，
请帮我妥善分工，我们小组加上我是三个人
```

- **模型输出要点**：

```
按评分表的六个任务，切成 35 / 30 / 35 三份，形成三条线：
设计线（需求 10 + 概念设计 15）、数据线（逻辑设计 15 + SQL 实现 15）、
程序线（JDBC 25 + 测试 10）；
关键交接点由不同成员独立完成（E-R 由组长画、关系模式由成员一独立转换），
以此形成交叉校验；另给出技术基线（MySQL 8.4 / JDK 21 / 库名 edu_ms）、
交付物目录对照与风险表。
```

- **人工判断**：

| 模型的输出 | 采纳情况 | 理由 |
|---|---|---|
| 35 / 30 / 35 三分法，与评分表六项一一对应 | 采纳 | 责任边界与评分项一致，扣分能落到人；组长 35 分中含统筹 |
| 进度按建议周期 3—4 周（28 天）编排 | **否决** | 组内实际只有 14 天，要求改为以"日"为单位重排 |
| 任务六拆分时把 6.1（系统测试）挂在组长名下 | **修改** | 6.1 按分工属成员二，组长负责 6.2（AI 辅助效果评价） |
| 技术基线（MySQL 8.4 / JDK 21 / edu_ms / 分层与命名约定） | 采纳 | 避免三人联调时字段与版本打架 |

- **发现的错误与修正**：
  1. **误判可用周期**：默认按作业建议的 3—4 周排期，未先确认实际工期，导致整份进度表返工；改为 14 天逐日安排，并新增"设计冻结点（D2）"与 G0—G7 关卡。
  2. **任务与人对不上**：把 6.1 分给组长，与"任务五（25 分）由成员二承担"的划分冲突；更正为组长承担 6.2。
- **最终落到**：`小组分工说明`（v1.1，14 天版）

## 二、2026-11-21　T1　需求分析

- **使用工具**：DeepSeek 编码助手
- **目的**：产出需求分析报告的结构与正文（角色、流程、核心数据、业务规则、需求三分类）
- **Prompt（原文）**：

```
你直接指导做吧，不允许直接进入我的工作区，只管我的任务1，2和6.2
```

- **模型输出要点**：

```
把任务一拆成 5 个动作：背景与范围 → 角色与操作 → 核心业务流程 → 核心数据与
业务规则 → AI 初稿与人工修改记录；
给出四类角色（学生 / 教师 / 教务管理员 / 系统管理员）及其"不做什么"；
五条流程（排课、选课、退课、成绩录入、统计）；
业务规则 B1—B16，每条标注落地方式【库】【程】【人】；
需求三分类（明确 / 隐含 / 待确认），并提出 Q1—Q5 五个待确认问题。
```

- **人工判断**：

| 模型的输出 | 采纳情况 | 理由 |
|---|---|---|
| 四类角色，含教务管理员 | 采纳 | 排课、开教学班、设选课窗口都归教务管理员，只写学生和教师会漏职责 |
| B1 写成"`student_id` 主键 + `student_no` 唯一" | **修改** | 同一实体两个编号属于过度建模，改为以学号作业务主键 |
| 每条规则标注【库】【程】【人】 | 采纳 | 规则必须能判定；"选课应公平"这类无法落地的表述不入表 |
| Q1—Q5 五个待确认问题及建议 | 全部采纳 | Q2 不做先修校验：否则要多一张课程自联系的多对多表，14 天工期不够 |

- **发现的错误与修正**：
  - **双主键/双标识**：模型给出的学生表同时有代理键 `student_id` 与业务键 `student_no`，且把唯一约束挂在后者。改为业务主键 `student_no`，并同步修改 B1、B2 与后续 E-R 的主键策略，避免任务三、四的建表返工。
- **最终落到**：`01_项目需求分析/需求分析报告.md`（第一至六节）

## 三、2026-11-21　T2　概念结构设计

- **使用工具**：DeepSeek 编码助手
- **目的**：把需求转成实体、属性、联系，并出 E-R 图
- **Prompt（原文）**：

```
开始任务2
```

- **模型输出要点**：

```
6 个实体：院系、专业、学生、教师、课程、教学班；
7 条联系，其中"选修"为学生与教学班的 M:N，并携带联系属性
select_time / score / attempt；
强调课程（Course）与教学班（TeachingClass）必须分离；
给出四个设计决策的论证（课程/教学班、院系专业两级、enrolled_count 冗余、
教室与时间段不做实体）；
输出陈氏 E-R 图与等价的 Mermaid 源码。
```

- **人工判断**：

| 模型的输出 | 采纳情况 | 理由 |
|---|---|---|
| 课程与教学班分离 | 采纳 | 同一门课不同学期由不同教师开设，合并会产生插入/删除/更新异常 |
| 成绩作为"选修"的联系属性 | 采纳 | 成绩只取决于"某学生 + 某教学班"，放学生或教学班表都无法表达多门课 |
| `enrolled_count` 作为冗余字段保留 | 采纳，追加要求 | 并发选课需锁行校验名额；代价是必须用事务维护一致，并补校验 SQL |
| `dept_no` 不放进学生表 | 采纳 | 学号 → 专业 → 院系 是传递依赖，放进去就不是 3NF |
| 用 Mermaid 直接表达 M:N | **修改** | Mermaid 的 erDiagram 不支持直接画 M:N，改以关联实体 `ENROLLMENT` 表达，并在文档中说明与 M:N 等价 |

- **最终落到**：`02_数据库概念设计/实体属性表与联系说明.md`、`ER图.png`、`ER图.mmd`

## 四、小结（供任务六 6.2 引用）

本次 AI 辅助在"结构搭建"上效率最高：需求报告的五段式结构、业务规则的分类口径、E-R 的实体划分，模型一次给出的框架基本可用，节省的是**组织与查漏**的时间。

但有两处必须靠自己的数据库知识判断：

1. **工期与分工是人的约束**，模型只能按文档里的"建议周期"推测，必须由组长先给出真实约束（14 天、3 人），否则整套排期不可用；
2. **主键与联系属性的归属**是模型最容易含糊的地方（双标识、成绩放错表），必须用"一个学生多门课"这类具体场景去验算，才能发现问题。
